# Slack Formatting — Mrkdwn & Block Kit

Slack has two delivery modes for rich content:

| Mode | How | Best for |
|------|-----|----------|
| **Mrkdwn text** | `send_message` / cron delivery | Simple messages, digests, quick notes |
| **Block Kit JSON** | curl to `chat.postMessage` with `blocks` array | Rich layouts: tables, cards, alerts, buttons |

Use the right mode based on the content. For route comparisons, corridor checks, or any structured data — **use Block Kit JSON**.

## CRITICAL: Pipe Tables in Mrkdwn = GARBAGE

**Slack mrkdwn does NOT render pipe tables.** If you output this:

```
| PRJ | Project | Health | Target |
|-----|---------|--------|--------|
| 001 | Alam Flora | 🟢 | 2026-09-05 |
```

It renders as **raw literal text** — ugly, unreadable, a wall of pipes. **NEVER output raw pipe tables in mrkdwn text.**

**Instead, use the Gateway Block Kit Pass-Through** (Part 4b). Output your response as JSON with a `blocks` array containing a `markdown` block. The gateway auto-detects and renders it as a proper table.

### The ONE pattern you need for tables:

```json
{"text": "Project Digest", "blocks": [
  {"type": "header", "text": {"type": "plain_text", "text": "📊 ACTIVE PROJECT DIGEST – 2 July 2026", "emoji": true}},
  {"type": "section", "text": {"type": "mrkdwn", "text": "*28 active* | 🟢 3 on track | 🟡 6 at risk | 🔴 16 overdue | 🟣 3 closing"}},
  {"type": "divider"},
  {"type": "markdown", "text": "| PRJ | Project | Health | Target | Progress | Risks |\n|-----|---------|--------|--------|----------|-------|\n| PRJ-001 | Alam Flora | 🟢 | 2026-09-05 | 15 trucks, AI deployment in progress | Server capacity limit at scale |\n| PRJ-003 | Kossan Industries | 🟣 | 2026-06-08 | Go-live completed 8 Jun | RM 7,500 outstanding |"},
  {"type": "context", "elements": [{"type": "mrkdwn", "text": "🔍 Generated by Your Company Project Agent · 2 Jul 2026"}]}
]}
```

**This is the ONLY acceptable way to send tables to Slack.** Raw pipe tables = fireable offense.

## Part 1: Mrkdwn Text (for send_message / cron delivery)

### Supported Syntax

| Style | Syntax | Example |
|-------|--------|---------|
| **Bold** | `*text*` | *bold text* |
| *Italic* | `_text_` | *italic text* |
| ~~Strikethrough~~ | `~text~` | ~strikethrough~ |
| `Code` | `` `text` `` | `inline code` |
| Code block | ` ``` ` `` `code` `` ` ``` ` | Multi-line monospace |
| Blockquote | `> text` | > quoted line |
| Bullet list | `• text` or `- text` | Indented lists |
| Numbered list | `1. text` | Auto-numbered |
| Link | `<https://url\|label>` | <https://example.com\|Click here> |
| Emoji | `:emoji:` | :rocket: :memo: :warning: |

### Headers
No `#` syntax in mrkdwn. Use `*bold*` as pseudo-headers or — better — use Block Kit `header` blocks for real headings.

### What to Avoid
- No `[text](url)` markdown links — use `<url|text>` instead
- No HTML tags — Slack strips them
- **☢️ NO pipe tables in mrkdwn** — they render as raw garbage text. If you must output a table, use the Block Kit pass-through (see CRITICAL section above)
- No walls of text — break into sections

### SELF-CHECK before sending to Slack
Scan your response for the `|` pipe character. If you see `| ... | ... |` without a surrounding JSON `blocks` wrapper, **STOP** — that's a raw pipe table. Rewrite it as Block Kit pass-through JSON.

## Part 2: Block Kit JSON (for Slack API delivery)

Send via curl to `chat.postMessage` with a `blocks` array. Example:

```bash
curl -s -X POST https://slack.com/api/chat.postMessage \
  -H "Authorization: Bearer $SLACK_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "channel": "C0XXXXXXXX",
    "text": "Fallback text for notifications",  # shown in push notifications
    "blocks": [ ... ]
  }'
```

Available block types for messages (up to 50 blocks per message):

| Block | Purpose |
|-------|---------|
| `header` | Large bold heading (150 chars max, plain text only) |
| `section` | Text body + optional fields (key-value pairs) + optional accessory |
| `divider` | Horizontal rule |
| `table` | Structured data grid (100 rows × 20 cols) |
| `alert` | Info/success/warning/error banner |
| `context` | Small metadata text with optional inline images |
| `actions` | Row of interactive buttons |
| `image` | Inline image |
| `markdown` | Formatted markdown block (pipe tables work here!) |
| `card` | Structured card with icon, title, subtitle, body, actions |
| `carousel` | Horizontal scrollable cards (up to 10) |
| `data_table` | Rich table with pagination, sorting, filtering |
| `video` | Embedded video player |

## Part 4: How to Choose

| Content Type | Use |
|-------------|-----|
| Simple text, short alerts | `send_message` with mrkdwn |
| Route/trip corridor checks | Block Kit JSON via curl (header + table + alert + card) |
| Structured data (stocks, scores) | Block Kit table block |
| Error/warning/success messages | Block Kit alert block |
| Multi-option comparisons | Block Kit card + carousel |
| Long digests with sections | Block Kit header + section + divider |
| Interactive follow-ups | Block Kit actions (buttons) |
| Push notification text | Always set `text` field in JSON payload |

## Part 4b: Gateway Block Kit Pass-Through (NEW)

The Hermes gateway now **automatically detects Block Kit JSON** in the agent's response text and sends it as proper Slack blocks instead of raw text.

### How it works

When the agent outputs a response that is valid JSON with a `blocks` array at the top level:

```json
{"blocks": [{"type": "header", "text": {"type": "plain_text", "text": "Hello"}}]}
```

The gateway:
1. Detects the JSON structure BEFORE the mrkdwn formatting pass (so it's not corrupted)
2. Passes the `blocks` array directly to Slack's `chat.postMessage`
3. Extracts a fallback `text` field from section/header blocks for push notifications
4. Falls back to plain mrkdwn text if Slack rejects the blocks payload

### What this means for agents

You can now output **inline Block Kit JSON** in your response text for Slack channels. No need to use `curl chat.postMessage` manually for Slack delivery — just write the JSON and the gateway handles it.

Important rules:
- The JSON must be the **entire response** (not embedded in surrounding text)
- Must have a top-level `blocks` key with a non-empty array
- Use the same Block Kit block types as documented in Part 2
- Always include a `text` key in the JSON for notification fallback
- Max 50 blocks per message

### Quick reference for curl delivery

```bash
# Send a Block Kit message to Slack channel
curl -s -X POST https://slack.com/api/chat.postMessage \
  -H "Authorization: Bearer $SLACK_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "channel": "C0XXXXXXXX",
    "text": "Corridor check results",
    "blocks": [
      { "type": "header", "text": { "type": "plain_text", "text": "🚄 Corridor Check", "emoji": true } },
      { "type": "divider" },
      { "type": "section", "text": { "type": "mrkdwn", "text": "Results here..." } }
    ]
  }'
```

## Part 5: What to Avoid

- Do NOT use `#` or `##` in mrkdwn text — use Block Kit `header` block instead
- Do NOT use `[text](url)` markdown links — use `<url|text>` in mrkdwn or `button.url` in Block Kit
- Do NOT use HTML tags — Slack strips them
- Do NOT send raw pipe tables in mrkdwn — they render as literal text
- Do NOT exceed 50 blocks per message
- Do NOT put mrkdwn formatting inside `table` block cells — use `rich_text` cell type instead
- Do NOT use `table` for data that needs clickable links inside cells — use `section` with fields instead
- Always include `text` field in Block Kit JSON payloads — it's shown in push notifications

## Part 6: Long-Content Handling (CRITICAL — prevent truncation)

### The Golden Rule: Write in sections, deliver in threaded messages

Do NOT cram everything into one message with many `section` blocks — every block still shows "Show more" on mobile if the text is long. Instead, **structure content into independent sections and send each logical chunk as its own Slack message, threaded under the root.**

This is proven: 3 threaded messages, each with 2-3 blocks, all fully visible. No truncation.

**Agent workflow when generating long replies for Slack:**

```
1. Plan message structure: "Header intro → Findings 1-3 → Findings 4-5 + next steps"
2. Each message gets its own `chat.postMessage` call (use `thread_ts` for replies)
3. 2-3 `section` blocks per message max, each section ~200-400 chars
4. Each section is self-contained — don't split mid-paragraph
```

### Block size limits

| Limit | Value | What happens |
|-------|-------|--------------|
| `mrkdwn.text` in any block | **3,000 chars** | Text cut off mid-sentence |
| `header.text` | **150 chars** | Header truncated |
| `text` (fallback, push notification) | **4,000 chars** | Fallback text trimmed |
| `blocks` array per message | **50 blocks** | Extra blocks dropped |
| Full payload (blocks + text) | **40,000 chars** | JSON rejected |

### When to split (decision tree)

```
Total content < 1,500 chars?
  → YES: Single message, 1-3 section blocks. Done.
  → NO: Split into multiple threaded messages.

Per message: 2-4 section blocks, each ~200-500 chars.
If > 4 messages needed → consider "TL;DR" root + detailed thread.
```

### PROVEN PATTERN — multi-message threaded delivery

```python
# MESSAGE 1: Root — header + intro
resp1 = slack_post([
    {'type': 'header', 'text': {'type': 'plain_text', 'text': 'Title Here'}},
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': 'Intro paragraph...'}},
    {'type': 'divider'}
])
root_ts = resp1['ts']

# MESSAGE 2: Thread reply — findings 1-3
resp2 = slack_post([
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': '*1. Finding One:* ...'}},
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': '*2. Finding Two:* ...'}},
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': '*3. Finding Three:* ...'}}
], thread_ts=root_ts)

# MESSAGE 3: Thread reply — findings 4-5 + next steps
resp3 = slack_post([
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': '*4. Finding Four:* ...'}},
    {'type': 'section', 'text': {'type': 'mrkdwn', 'text': '*5. Next Steps:* ...'}},
    {'type': 'divider'}
], thread_ts=root_ts)
```

### What does NOT work (and why)

| Approach | Result |
|----------|--------|
| One message, 8+ section blocks | Most blocks show "Show more", reader scrolls forever |
| One section with 4000 chars | Hard-truncated at 3000 chars mid-sentence |
| Multiple messages NOT threaded | Scattered in channel, impossible to follow |
| Splitting mid-paragraph between messages | Each message incomprehensible standalone |

### Real-world failure pattern

Agent generates 4,200 chars of research → formats as ONE `section.text` → Slack shows first 3,000 chars → **cut off mid-sentence with no warning**.

**Rule: Never put more than 2,500 chars in a single mrkdwn.text field. Split into threaded messages at natural section boundaries.**

## Part 7: File Uploads to Slack

`MEDIA:` prefix only works for Telegram delivery. Slack does NOT support `MEDIA:` — you'll just get the path rendered as plain text. Use the Slack file upload API instead.

### Quick check: should you upload or link?

| If... | Do this |
|-------|---------|
| File is on disk, user wants it in Slack | Upload via 3-step flow below |
| File is already on GDrive/cloud | Send a link instead (faster, no API calls) |
| User says "send the .md file" | Upload. They want it right there. |

### The 3-step upload flow (files.upload is DEPRECATED)

```python
import json, urllib.request, urllib.parse

# Step 1: Get upload URL — MUST use form-encoded, NOT JSON
data = urllib.parse.urlencode({'filename': fn, 'length': fsize}).encode()
r1 = json.loads(urllib.request.urlopen(urllib.request.Request(
    'https://slack.com/api/files.getUploadURLExternal',
    data=data,
    headers={'Authorization': 'Bearer ' + token,
             'Content-Type': 'application/x-www-form-urlencoded'}
)).read())
upload_url = r1['upload_url']
file_id = r1['file_id']

# Step 2: POST raw bytes to the upload URL
with open(filepath, 'rb') as fh:
    urllib.request.urlopen(urllib.request.Request(upload_url, data=fh.read(), method='POST'))

# Step 3: Complete — form-encoded, NOT JSON
data3 = urllib.parse.urlencode({
    'files': json.dumps([{'id': file_id, 'title': 'Display Title'}]),
    'channel_id': CHANNEL_ID,
    'initial_comment': 'Optional caption'
}).encode()
r3 = json.loads(urllib.request.urlopen(urllib.request.Request(
    'https://slack.com/api/files.completeUploadExternal',
    data=data3,
    headers={'Authorization': 'Bearer ' + token,
             'Content-Type': 'application/x-www-form-urlencoded'}
)).read())
```

### Critical gotchas (learned the hard way)

| Trap | Fix |
|------|-----|
| `files.upload` API | **Deprecated.** Returns `method_deprecated`. Must use 3-step flow. |
| JSON body on steps 1 or 3 | **Returns `invalid_arguments`.** Must use `application/x-www-form-urlencoded`. |
| `channels` param | **Renamed to `channel_id`** (singular). Old plural name rejected. |
| `MEDIA:` in Slack | **Telegram only.** Slack renders it as literal text with a broken file icon. |
| Async processing | File may not appear instantly. Slack scans uploads async. |
| Token access | Slack tokens are in `.env` files, redacted by read_file. Extract via: `grep '^SLACK_BOT_TOKEN=' .env | cut -d= -f2- | tr -d '\"'` |
